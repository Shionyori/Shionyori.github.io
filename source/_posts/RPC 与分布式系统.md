RPC（远程过程调用）允许程序以调用本地函数的方式调用另一台机器上的函数，是分布式系统中机器间通信的基础方式。本文按 RPC 的组成部分（契约、存根、注册中心、治理能力）逐一说明，再介绍分布式系统的部署与协作方式。

---

# RPC 的核心机制

## 什么是 RPC

**RPC（Remote Procedure Call，远程过程调用）** 让调用方像调用本地函数一样调用另一台服务器上的函数。调用方代码中不直接出现 `socket()`、`connect()`、`send()`、`recv()`，也不处理序列化格式和 HTTP 请求头，这些工作由 RPC 框架完成。

一次 RPC 调用的处理过程：

1. **客户端存根（Client Stub）**：调用方实际调用的是框架生成的代理对象，它把方法名和参数打包。
2. **序列化**：把内存中的对象转换成字节流（如 Protobuf）。
3. **网络传输**：通过 socket 把字节流发送到目标服务器。
4. **服务端存根（Server Stub）**：接收字节流并反序列化，调用真正的业务逻辑，再把返回值序列化后传回。

## 契约与代码生成

两个独立进程要互相调用，必须先约定接口。以用户服务调用支付服务为例：用户服务需要确认支付服务提供了 `DeductBalance()`、该方法接受哪些参数，这一约定通过**契约（Contract）**实现：

- 用中立语言（Protobuf / Thrift）编写接口定义文件 `.proto`，只声明方法名和参数类型，不写实现。
- 客户端和服务端依赖同一份契约，分别生成代码：
  - **服务端**生成骨架（Skeleton），在其中填入业务逻辑。
  - **客户端**生成存根（Stub）：方法签名与远端一致，内部只做参数打包与网络发送，不含业务实现。

{% note info %}
方法签名在编译期由契约确定（生成的 Stub 代码），服务实例的地址在运行期由注册中心提供。这两件事相互独立。
{% endnote %}

## RPC 与 HTTP 接口的区别

| 维度 | RPC（如 gRPC） | HTTP + JSON |
| --- | --- | --- |
| 序列化 | Protobuf（二进制，体积小、解析快） | JSON（文本，体积大、解析慢） |
| 连接方式 | 长连接 + 多路复用 | 短连接或复用连接 |
| 关注点 | 动作 / 行为（执行某个计算） | 资源（对实体的增删改查） |
| 适用场景 | 内部微服务之间的高频调用（东西向流量） | 对外接口、前端直连（南北向流量） |

# 服务发现与注册中心

## 注册中心的角色

注册中心（Nacos / Consul / Etcd）保存各服务实例的 IP 与端口列表，不参与业务数据的转发：

1. 服务启动时，向注册中心注册自己的 IP 和端口。
2. 调用方启动时，从注册中心拉取目标服务的 IP 列表，缓存在本地内存。
3. 实际调用时，存根从本地缓存选择一个 IP，直接把请求发给目标服务器——请求不经过注册中心。

{% note info %}
注册中心只在服务注册、注销和地址列表定时刷新时被访问。业务请求由客户端直接发送到业务服务器，服务发现走独立的管理通道，两者互不影响。
{% endnote %}

## 注册中心的部署形态

注册中心需要用 3 或 5 台独立服务器组成集群（取奇数台，通过分布式共识算法选主），并与承载业务的服务隔离部署。只部署一台时，注册中心本身会成为单点故障。

注册中心全部宕机时，已建立的调用仍可继续：调用方内存中缓存了服务地址列表；但新注册的服务无法被发现，扩容的节点收不到流量，直到注册中心恢复。

# RPC 框架的治理能力

代码生成只是 RPC 框架功能的一部分。生成存根解决“如何调用”，框架还需要在运行时处理调用过程中出现的问题：

- **负载均衡**：从缓存的地址列表中选择目标节点（轮询 / 随机 / 按权重）。
- **熔断降级**：连续调用某节点失败达到阈值后，暂时停止向该节点发送请求，防止故障扩散到其他节点；节点恢复后自动放行。
- **超时控制**：为每次调用设置超时，超时后快速失败，或重试其他节点。
- **链路追踪**：每次调用生成全局 TraceID 并在调用链各节点间传递，用于定位慢节点和错误点。

{% note info %}
通信层负责完成一次调用的网络收发，治理层负责在节点宕机、超时、网络异常时保证调用可用。调用规模小时这些能力可以不配置；在线上环境中没有负载均衡、超时与熔断，任一节点故障都会直接造成部分调用失败。
{% endnote %}

手写存根无法替代 RPC 框架的原因在于：自行实现存根只能处理序列化和收发，负载均衡、重试、熔断等逻辑需要逐个写进业务代码（例如在 `placeOrder()` 内部处理重试与降级），业务代码会因此混杂大量与业务无关的分支。框架将这些能力以拦截器形式挂在存根外层，业务代码保持为普通方法调用。

{% note info %}
RPC 框架的价值在于把服务发现、负载均衡、故障容错这些分布式问题集中到框架内部处理，业务代码不需要感知远端调用的网络细节。因此 RPC 框架不仅是协议实现，同时承担运行时治理。
{% endnote %}

# 分布式系统的部署与代码组织

## 分布式系统的好处

- **水平扩展**：流量增大时增加机器数量，性能随机器数近似线性提升，而不是更换更强的单机。
- **高可用**：部分机器宕机时，负载均衡把流量切换到其余节点，调用不中断（故障转移）。
- **独立部署**：各服务独立发布，团队之间以接口契约为边界协作，互不阻塞。
- **异地容灾**：数据在多个机房备份，单个机房故障不至于导致服务整体不可用。

> 分布式系统通过多台服务器协同工作获得更高的扩展能力与可用性。代价同样明确：网络不可靠、数据一致性需要取舍（CAP 理论）、运维复杂度明显高于单机。

## 部署的两种情况

多台服务器上运行的程序是否相同，取决于部署目标，分两种情况：

- **水平扩展**：同一服务部署到多台机器，程序完全相同，共享同一个数据库，前端由负载均衡分发流量。
- **微服务拆分**：不同服务部署在不同机器，程序各不相同，通过 RPC 框架互相调用。

部署时需要区分服务是否有状态：无状态服务（用户、订单服务）可以复制到任意数量的机器；有状态服务（数据库、Redis）各实例数据不同，需要分片规则和主从同步，不能简单复制代码。

生产环境的部署是一条自动化流水线（CI/CD）：提交代码 → 自动编译 → 打成 Docker 镜像 → 推送到镜像仓库 → 由 Kubernetes 调度到多台服务器启动。流量增大时自动扩容，回落时自动缩容。

## 代码组织方式

微服务拆分后，代码按**业务边界**组织（用户模块、订单模块、支付模块），而不是按技术层次组织。常见的两种方式：

- **多仓库（Multi-Repo）**：每个微服务一个独立 Git 仓库，权限隔离、独立发版、技术栈自由。
- **单仓库（Monorepo）**：所有服务放在同一仓库中按目录划分，修改可原子提交、版本统一。

无论哪种方式，**公共契约（.proto 文件）和公共工具库需要独立管理并打版本**：服务端升级契约后，客户端可以继续用旧版本调用，互不影响（依赖版本解耦）。

单个微服务内部也按职责分层（如 DDD 的 api / domain / infra）：`domain` 层只包含业务逻辑，不依赖具体的数据库和缓存实现；需要替换基础设施组件时，只改动 `infra` 层。

# 分布式系统的协作方式

## RPC 之外的协作手段

分布式系统的节点之间需要通信，RPC 是其中一种方式，不是唯一方式：

| 方式 | 特点 | 适用场景 |
| --- | --- | --- |
| 消息队列（MQ） | 异步、解耦、非阻塞 | 削峰填谷、不需要立即返回结果的场景（发邮件、扣库存） |
| 共享存储 / 数据库轮询 | 实现简单，延迟高 | 简单或遗留系统 |
| HTTP REST API | 本质也是一种远程调用 | 对外接口、跨语言简单调用 |

实际系统中两种方式经常并用：需要同步等待结果的调用用 RPC，可以延迟处理的操作（发邮件、扣库存等）用消息队列。

## RPC 与分布式系统的关系

{% note info %}
RPC 不改变网络传输本身，只改变程序调用远端功能时的编程方式。无论用 gRPC 还是直接写 socket，线路上传输的都是协议定义好的字节流。RPC 框架把序列化、寻址、超时、重试等处理集中到框架内部，业务代码不直接接触这些细节。
{% endnote %}

区分两层含义：

- **广义 RPC（远程调用）**：通过网络调用远端程序提供的能力。HTTP 调用、数据库客户端协议都属于这一类，是分布式系统节点间交互的基本形式。
- **狭义 RPC 框架（gRPC / Dubbo）**：提供接口定义、代码生成与运行时治理的完整实现，统一处理服务寻址、序列化、超时与错误码，使业务代码可以用本地调用方式完成跨网络调用。
