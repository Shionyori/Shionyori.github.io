RPC（远程过程调用）让跨机器的调用看起来像本地调用，是分布式系统中最重要的通信抽象。本文深入 RPC 的核心机制（契约、存根、注册中心、治理能力），再落到分布式系统的部署与协作方式。

---

# RPC 的核心机制

## 什么是 RPC

**RPC（Remote Procedure Call，远程过程调用）** 让调用者像调用本地函数一样，去调用另一台服务器上的函数。代码里看不到 `socket()`、`connect()`、`send()`、`recv()`，也看不到序列化和 HTTP 请求头——这些都由 RPC 框架完成。

一次 RPC 调用的完整流程：

1. **客户端存根（Client Stub）**：调用的是代理对象，它把方法名和参数打包。
2. **序列化**：把内存中的对象转成字节流（如 Protobuf）。
3. **网络传输**：通过 socket 把字节流发到目标服务器。
4. **服务端存根（Server Stub）**：接收后反序列化，调用真正的业务逻辑，再把返回值序列化传回。

## 契约与代码生成

两个独立进程之间不可能凭空知道对方有什么方法。用户服务"知道"支付服务有 `DeductBalance()`，靠的是**契约（Contract）**：

- 用中立语言（Protobuf / Thrift）编写接口定义文件 `.proto`，只声明方法名和参数类型，不做实现。
- 客户端和服务端依赖同一份契约，分别生成代码：
  - **服务端**生成骨架（Skeleton），往里面填充真正的业务逻辑。
  - **客户端**生成存根（Stub）——一个"假的"方法，内部只有网络打包发送的逻辑。

{% note info %}
**编译时知道"方法长什么样"（契约生成的 Stub），运行时才知道"服务在哪"（注册中心）——这是两件分离的事。**
{% endnote %}

## RPC 与 HTTP 接口的区别

| 维度 | RPC（如 gRPC） | HTTP + JSON |
| --- | --- | --- |
| 序列化 | Protobuf（二进制，体积小、解析快） | JSON（文本，体积大、解析慢） |
| 连接方式 | 长连接 + 多路复用 | 短连接或复用连接 |
| 关注点 | 动作 / 行为（执行某个计算） | 资源（对实体的增删改查） |
| 适用场景 | 内部微服务之间的高频调用（东西向流量） | 对外接口、前端直连（南北向流量） |

# 服务发现与注册中心

## 注册中心的角色

注册中心（Nacos / Consul / Etcd）不是业务请求的中转站，而是**服务地址簿**：

1. 服务启动时，向注册中心注册自己的 IP 和端口。
2. 调用方启动时，从注册中心拉取目标服务的 IP 列表，缓存到本地内存。
3. 实际调用时，存根从本地缓存选择一个 IP，**直接**向目标业务服务器发请求——请求不经过注册中心。

{% note info %}
**注册中心只在启动时和心跳时使用**：启动时用来查地址，运行中定时刷新本地缓存、剔除宕机的节点。业务请求走业务端口，服务发现走管理端口，各走各的路。
{% endnote %}

## 注册中心的部署形态

注册中心必须是**由 3 或 5 台独立服务器组成的集群**（取奇数台，靠分布式共识算法选主），并与承载业务的服务隔离部署。如果只部署一台，它就成了单点故障。

如果注册中心全部宕机，业务调用依然可以运行——因为调用方本地缓存着服务地址列表；但系统会失去自动发现新服务的能力（新扩容的机器流量进不来），直到注册中心恢复。

# RPC 框架的治理能力

RPC 框架并不仅仅是"代码生成器"。生成存根只是最表面的一层，框架真正的价值在**运行时治理**：

- **负载均衡**：从本地缓存的 IP 列表中选择目标节点（轮询 / 随机 / 按权重）。
- **熔断降级**：连续调用某节点失败后，自动将其拉入黑名单，避免雪崩。
- **超时控制**：为每次调用设置超时，超时后快速失败或重试到其他节点。
- **链路追踪**：每次调用生成全局 TraceID，贯穿整个调用链，方便定位慢节点。

{% note info %}
**通信代理层负责屏蔽网络通信，治理层负责解决分布式环境下的容错问题。** 业务量小时治理是附属品；但在大规模生产环境中，治理直接决定系统死活——没有负载均衡、熔断和服务发现，通信逻辑再完善也撑不过线上环境的故障频发。
{% endnote %}

这也是"自己写模板"无法替代 RPC 框架的原因：手写代码生成器只能生成纯网络收发代码，治理逻辑会侵入业务代码（在 `placeOrder()` 里手动写重试、熔断），把业务逻辑弄得面目全非。而框架在存根外层自动包裹拦截器链，治理与业务完全解耦。

{% note info %}
**正是因为封装了治理能力，才有了使用 RPC 框架的理由。** 更严谨的说法是：RPC 框架不只是 RPC 协议实现，更是一个"分布式系统语义抽象层"，把服务发现、负载均衡、故障容错这些分布式概念直接植入每一次函数调用中。
{% endnote %}

# 分布式系统的部署与代码组织

## 分布式系统的好处

- **水平扩展**：流量增大时加机器即可，性能近似线性提升（而非换更贵更强的单机）。
- **高可用**：部分机器宕机时，负载均衡把流量切给其余节点，用户无感知（故障转移）。
- **独立部署**：各服务独立发布，团队之间通过接口契约协作，互不阻塞。
- **异地容灾**：数据多机房备份，单点故障不至于导致整体不可用。

> 分布式系统的本质是"用多台廉价机器加上复杂的软件逻辑，替代一台昂贵到买不起的超级单机"。它的副作用同样显著：网络不可靠、数据一致性需要妥协（CAP 理论）、运维复杂度剧增。

## 部署的两种情况

多台服务器上部署的是不是相同程序，取决于说的是哪种部署：

- **水平扩展**：同一服务部署到多台机器，程序完全相同，共享同一个数据库，前面由负载均衡分发流量。
- **微服务拆分**：不同服务部署在不同机器，程序完全不同，通过 RPC 框架互相调用。

关键区分是**有状态与无状态**：无状态服务（用户、订单）可以随意复制到多台机器；有状态服务（数据库、Redis）内部数据各不相同，需要分片规则和主从同步，不能简单复制代码。

生产环境的部署是一条自动化流水线（CI/CD）：提交代码 → 自动编译 → 打成 Docker 镜像 → 推送到镜像仓库 → 由 Kubernetes 调度到多台服务器启动。流量增大时自动扩容，回落时自动缩容。

## 代码组织方式

微服务拆分后，代码按**业务边界**组织（用户模块、订单模块、支付模块），而非按技术层组织。两种主流方式：

- **多仓库（Multi-Repo）**：每个微服务一个独立 Git 仓库，权限隔离、独立发版、技术栈自由。
- **单仓库（Monorepo）**：所有服务在同一仓库中按目录区分，原子化修改、统一版本。

无论哪种方式，**公共契约（.proto 文件）和工具库必须独立管理并打版本**：服务端升级契约后，客户端可以继续使用旧版本调用，互不影响（依赖版本解耦）。

单个微服务内部也要分层（如 DDD 的 api / domain / infra）：`domain` 只写纯业务逻辑，不依赖具体的数据库和缓存实现；要替换技术组件时只需改动 `infra` 层。

# 分布式系统的协作方式

## RPC 之外的协作手段

分布式系统的基石是**网络通信**，RPC 只是对通信的一种封装抽象，并非唯一实现方式：

| 方式 | 特点 | 适用场景 |
| --- | --- | --- |
| 消息队列（MQ） | 异步解耦、非阻塞 | 削峰填谷、不需要立刻知道结果的场景（发邮件、扣库存） |
| 共享存储 / 数据库轮询 | 简陋但能跑，延迟高 | 极简或遗留系统 |
| HTTP REST API | 本质上也是一种远程调用 | 对外接口、跨语言简单调用 |

现实中的大型系统通常同时使用两种手段：必须立刻知道结果的调用用 RPC（同步），可以延迟处理的用消息队列（异步）。

## RPC 与分布式系统的关系

{% note info %}
**RPC 没有提供新的实现路线，它是一次封装、一个抽象层。** 无论用 gRPC 还是裸写 socket，网线上走的都是同样的字节流。RPC 的贡献是把分布式编程的复杂度从业务代码转移到框架内核，让业务开发者可以用单机编程的思维去构建跨网络的系统。
{% endnote %}

区分两层含义：

- **广义 RPC（远程调用）**：任何"跨进程调用远端函数"的行为都是 RPC，是分布式系统交互的必要手段。
- **狭义 RPC 框架（gRPC / Dubbo）**："本地调用模拟器"，核心价值是降低分布式编程的复杂度，并将网络故障处理标准化（统一的错误码、链路追踪）。
